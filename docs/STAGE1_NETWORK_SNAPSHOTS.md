# Этап 1: ограниченная сеть и проверяемая передача снимков

12.10.2026, [PR #3](https://github.com/WestDed/TransportFever3-Multiplayer/pull/3), база — PR #2, без слияния в main. Лицензия MIT и авторство MPFever сохранены. Игры, Steam-сессии и настоящих `.sav` нет.

## Исправленные отказы

- `StreamReader.ReadLine()` позволял накопить произвольную строку. Реальные Relay/Client теперь используют `BoundedLineReader`: максимум 4 MiB данных плюс 256 байт заголовка, строгий UTF-8, отказ на усечённой строке. Лимит проверяется во время чтения, до декодирования строки.
- До join запрещены другие сообщения; повторный join закрывает соединение. Версия TCP-протокола — **2**, клиент с прежним `{}` получает `reject` и отключение. Lua file IPC сохраняет существующий формат. Старые и новые лаунчеры нельзя смешивать.
- Первый пакет должен завершиться за 10 с; начатый пакет — за 60 с. Для соединения без начатой строки нет idle timeout: загрузка игры может быть долгой. Максимум восемь TCP-соединений, включая незавершённые join.
- `GameLink` больше не выделяет массив размера всего прироста файла. По 256 KiB за poll, буфер 8 KiB, ограничение незавершённой строки. Ошибочная/слишком большая IPC-строка пропускается до LF, следующие строки сохраняются. Chat/menu ограничены 16 KiB.
- Каждый peer имеет отдельный `BoundedOutbox`: максимум 8 MiB и 128 кадров **включая кадр в отправке**. Обычный broadcast не ждёт медленного сокета; переполнение отключает этого peer. File worker ждёт место только в своей очереди, до 120 с. Socket write timeout — 60 с. Это ограничение прогресса, а не гарантированная скорость сети.
- Удалено `ReadAllBytes(save)` и сборка полного файла из base64-массивов. Хост держит read-only handle, вычисляет SHA-256 и читает по 256 KiB отдельно для каждого peer. Общий broadcast больше не содержит цикл блокирующих записей всему списку.
- Приём требует `resync_begin {id,transfer,bytes,n,sha256}`. Проверяется положительный целый id, случайный transfer из 32 hex символов, hash из 64 hex, 1..1 GiB, точное число частей (максимум 4096). Это предварительный бюджет безопасности; размер Gigantomaniac по нему не оценивался.
- `resync_file {id,transfer,i,n,data}` проверяет принадлежность, индекс, размер последней части, канонический base64. Перестановка частей допустима; одинаковая повторная часть не увеличивает прогресс, отличающаяся отвергается. Completed/expired/старые id не запускают передачу повторно.
- Один временный `.part` на локальную игру, bitmap до 4096 флагов. SHA-256 проверяется только после всех частей. Повреждённый файл удаляется, не отправляется в загрузку. Нет частей 3 минуты или общее время >30 минут — очистка; disconnect/EndSession также удаляет partial file. Эти пределы не являются RAM-бенчмарком.
- В каждом локальном каталоге сохранений сначала создаётся временный файл, выполняется `Flush(true)`, затем `File.Replace`/`Move`. Нет неатомарного copy-over fallback. Ошибка сохраняет прежний `.sav`; загрузка запрашивается только после хотя бы одного успешного назначения. Между несколькими каталогами общей атомарной транзакции нет.
- Удалён приём удалённого `save_done`. Лаунчер ждёт подтверждение **с нужным id** от host GameLink. Клиент сообщает `resync_received` только после проверки и записи; его `hello` закрывает ожидание reload после receipt. Неудачная передача или отсутствие ready больше не запускает `SetSpeed` в finally: сессия остаётся на паузе.
- Добавлена проверка generation для отмены старого resync при окончании сессии. Очередь команд на границе save/load пока требует отдельного изменения; отсутствие этой гарантии не скрывается.

## Выполненная проверка

На [Actions run 38208415069](https://github.com/WestDed/TransportFever3-Multiplayer/actions/runs/38208415069) реальные C# компоненты успешно прошли **70 проверок** на Ubuntu и Windows. Проверены исходный код Core/NetworkIO/Snapshots, а не повторение алгоритмов на Python:

- настоящий TCP Relay/Client, spoofed From, версия join, фрагменты UTF-8, timeout начатой строки, EOF;
- source → bounded queue → TCP → receiver → итоговый файл с точными исходными байтами;
- неверные manifest/index/size/base64/transfer, duplicate/out-of-order/stale, SHA-256 corruption, неполная передача и очистка;
- отказ файловой системы, сохранность предыдущего final save, атомарная замена;
- заблокированный writer и независимый прогресс другого writer, ограничение очереди с in-flight bytes.

Python/Lua: 44 теста, 43 PASS и прежний expected failure AUD-04. C# LuaLit: 46 PASS. Полная сборка прежнего net48 EXE и freestanding x64 DLL успешно выполнена в первом [run 38207896457](https://github.com/WestDed/TransportFever3-Multiplayer/actions/runs/38207896457). В CI добавлена проверка PE/zip/лицензии и build-manifest с `gameTested=false`. Финальный run и его итог фиксируются в описании PR.

Воспроизведение без игры:

```sh
python -m pip install -r tests/requirements-offline.txt
python -m unittest discover -s tests -p 'test_*.py' -v
dotnet run --project tests/offline/Offline.csproj --configuration Release
```

Windows: `./tests/test_lualit.ps1`, `cmd /c build.bat`, `./tests/verify_windows_build.ps1`; требуются VS C++ tools, MSBuild и .NET 4.8 targeting pack. CI обеспечивает эту среду. Тестовый console target net8; полный production target net48 собирается отдельной обязательной job.

## Граница доказательства и следующий шаг

Это проверки файла со случайными байтами, сокетов и сборки. Они не исполняют WinHTTP hooks, не подтверждают корректность игровых `.sav`, save/load callbacks, экономики, progression или поведения на больших картах. `hello` остаётся заявлением клиента о готовности; подпись хеша не аутентифицирует хост и не проверяет семантику мира. TCP не шифруется, identity по имени и доверие sid требуют следующего PR. Центральный порядок/replay автору нельзя включать, пока не согласованы GUI/native holds и не пройден игровой gate.

Следующее: digest реестра, повторное подключение по случайному credential, схемы команд и привязка компании. Затем чистый компонент epoch/order/recovery и воспроизводимый TCP нагрузочный стенд. Движковые права/цены проверяются после покупки игры по TESTING.md.
