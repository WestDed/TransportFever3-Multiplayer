# Проверка изменений Claude: подключение и пауза

Дата: 22.10.2026. Проверены [PR #21](https://github.com/WestDed/TransportFever3-Multiplayer/pull/21), его commit `98f3363338fa204aaeb1ac7461d8b17c7a9cea7f` и текущая main `8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2`. Их исходное дерево совпадает: `8bccd8a1ab001c83c3516ee21d91bab4d3c75dec`. База PR — `52b47bd`. [PR #20](https://github.com/WestDed/TransportFever3-Multiplayer/pull/20) остаётся открытым и в это дерево не входит.

## Оценка

Работа полезная: найдены реальные причины блокировки паузы и обрыва медленных передач. Сжатие имеет ограничения размера, полный SHA сохранён, добавлены исполняемые тесты. Заявленные 305 Python/Lua-тестов и 730 C#-проверок воспроизводятся; main имеет зелёный CI.

При этом решение паузы частично заменяет ожидание правильного состояния продолжением с неизвестным состоянием. Один новый дефект порядка команд воспроизведён ниже. Принудительное продолжение после неудачной синхронизации — сознательная новая политика, требующая изменения для стабильного совместного мира. Кроме того, в main остались прежние дефекты жизненного цикла докачки. Этот отчёт и примеры не изменяют production-код и не доказывают работу TF3.

## Подтверждённые замечания

### P1 — зависимая команда теряется после таймаута создания

Новое поведение: [runPausedActions, строки 3763–3765](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/mod/mpfever_1/content/mpfever_bridge.script.lua#L3763) снимает `G.pausedCreating` после трёх запросов восстановления, даже если callback создания не пришёл. Затем очередь обрабатывается дальше.

Сценарий: во время паузы получены «купить транспорт» и следующее «назначить этот транспорт на линию». Ответ о покупке задерживается. После снятия барьера назначение попадает в настоящий `executeActionOnce`, где ещё отсутствует привязка `V1`: команда получает `DESYNC unresolved: V1`. Обработчик записывает отказ, а scheduler удаляет её из `G.pendingPaused`. Поздний callback покупки создаёт привязку, но назначение уже потеряно.

Воспроизведение использует настоящие `runPausedActions`, `executeActionOnce` и wrapper `executeAction`. Подставлены асинхронный движок и resolver с контрактом «нет binding → unresolved»; игра не запускается. Результат на main:

```text
Before purchase callback: DESYNC unresolved: V1 pending=0
After callback: binding=777 engine calls=1 pending=0
FAIL: Dependent assignment was permanently rejected before the purchase response
```

При подстановке scheduler из базы `52b47bd` та же проверка порядка проходит: зависимая команда остаётся в очереди. У базы есть другая известная проблема — игнорирование позднего callback после таймаута; это не оправдывает исполнение зависимых действий раньше создания объекта. Существующий новый тест `test_missing_answer_repeats_recovery_then_releases_hold` проверяет число применённых команд, но его заглушка `executeAction` не проверяет binding.

Рекомендация: принимать поздний ответ текущей операции, повторять recovery, сохранять зависимые команды до подтверждённого создания или корректного завершения операции с явным отказом/отменой её зависимостей. Таймаут сам по себе не должен разрешать проигрывание неподготовленных команд.

### P1 — обычная кнопка скорости разрешает общую симуляцию после failed recovery

Это **сознательное изменение политики**, а не скрытая ошибка `RecoveryGate`. [RecoveryGate.Resume](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/launcher/RecoveryGate.cs#L27) разрешает хосту очистить failure, retries и срок следующего повтора. [SetSpeed](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/launcher/MainForm.cs#L1495) после этого рассылает общую скорость через `BroadcastSession`; отстающие подключённые игроки не исключаются и не проходят новый gate готовности.

Компонентное наблюдение: `Freeze → Failure → Resume(host)` разрешено; следующий `Resume(client)` тоже разрешён, `Failed=false`. Новые тесты прямо требуют такой политики. Она устраняет административный замок, но не устанавливает равенство миров и не подтверждает загрузку незавершившего recovery клиента. Реальная порча финансов этим тестом не воспроизведена; код разрешает продолжение в условиях, от которых прежний gate защищал.

Для проекта с общими грузами, городами и независимыми бюджетами следует отделить «хост продолжает один» от «все продолжают синхронно». Безопасный выход — исключить неготовых клиентов из активного состава и дать им свежий снимок при возвращении либо завершить восстановление до общей симуляции. Обычная кнопка x1 не должна молча заменять проверку готовности. Предупреждение только в логе недостаточно для осознанного выбора игрока.

### P2 — прежние ошибки докачки остались в main

Эти ошибки **не добавлены Claude**. Изменение `Expire → Retain` исправляет сохранение partial при истечении срока, но не все остальные пути:

| Сценарий | Текущий код и наблюдение |
|---|---|
| Пользователь нажимает Cancel | [EndSession](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/launcher/MainForm.cs#L834) вызывает `receiver.Dispose()`. Отдельно исполненный production Dispose удаляет `download.part`. Это наблюдение API + проверка вызова, не новое исполнение WinForms на Linux. |
| Отмена во время проверки прежнего partial | [OpenResumable](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/launcher/SnapshotResume.cs#L89) ловит `OperationCanceledException` общим `catch`, вызывает `Clear()` и удаляет проверяемый checkpoint. Реальная файловая регрессия падает. |
| Новый receiver начинает передачу до завершения работы старого CompletedSnapshot | [CompleteIfReady](https://github.com/WestDed/TransportFever3-Multiplayer/blob/8eb16ee4c08198162f9c1e80560a0f0ebc18b5d2/launcher/Snapshots.cs#L337) передаёт старому объекту тот же фиксированный путь `download.part`, который использует новая передача. На Linux Dispose старого объекта удаляет новый файл; регрессия падает. На Windows открытый файл может вместо удаления вызвать IOException; такой исход здесь не исполнялся. |

Штатное закрытие окна также не вызывает явный `Suspend` всех активных receivers. В PR #20 эти пути и изоляция завершённого файла уже исправлены, включая настоящий WinForms Cancel/Close на Windows. Их нужно согласовать с protocol 12 и перенести в main; сборка пакетов из двух веток не заменяет интеграцию исходников.

### P2 — две несовместимые сборки имеют один номер .7

Main/PR #21: `0.3.7-westded.7-experimental`, FileVersion `0.3.7.7`, **protocol 12**. Открытый PR #20: тот же номер и FileVersion, **protocol 11**. Это следствие параллельной работы от одной базы; номер .7 не определяет совместимость. Проверка протокола откажет смешанной паре, что правильно, но пользователь видит два разных пакета с одинаковым названием.

При интеграции следует выпустить новый однозначный номер пакета, сохранить protocol 12 для сжатых частей и обновить полный комплект на обоих ПК. PR #20 нельзя предлагать как готовое слияние без разрешения конфликтов и повторных проверок.

## Что обоснованно исправлено

- Жёсткий 30-минутный предел заменён отслеживанием прогресса и общим пределом 4 часа. Это устраняет принудительный обрыв продолжающейся медленной передачи. Клиент по-прежнему имеет отдельный idle-предел 180 секунд; host progress — 600 секунд. Увеличение сроков не повышает пропускную способность.
- Прогресс исходящей передачи считается по snapshot-кадрам, переданным в сокет, а не по постоянным служебным сообщениям. Это не выдаётся за подтверждение получения клиентом.
- Сжатие части применяется при экономии не меньше 1/8, несжимаемые данные сохраняют raw-путь. Входной/выходной размер ограничен частью; итоговый SHA всего файла обязателен. Эффект на настоящем пользовательском .sav не измерен.
- Автоматические повторы recovery и сохранение `replay_failed`, пришедшего во время cooldown, устраняют реальные тупики. Исправление позднего callback полезно, если сохранить порядок зависимых команд.
- Таймер очистки теперь обрабатывает дополнительные ожидаемые файловые исключения. Документация, номер протокола, упаковка и тестовые проекты обновлены.

Бесконечный `resyncFailed` в прежнем коде действительно был дефектом: любой провал мог оставить стандартное возобновление заблокированным до перезапуска. Автоповтор/явный путь восстановления нужны; замечания относятся к способу разрешить продолжение с подключёнными участниками и к обходу незавершённой команды.

## Проверки и воспроизведение

Повторено локально на точном исходном дереве main: **305 Python/Lua tests PASS**, **730 C# checks PASS** на net8/Linux. Проверен [main CI 39352003265](https://github.com/WestDed/TransportFever3-Multiplayer/actions/runs/39352003265): 7/7 jobs PASS, в том числе фактический Windows net48 (730), сборка EXE/DLL/ZIP и настоящее окно WinForms (34). Изменённый AutoStart и host override целиком в игре не проверены; часть новых тестов проверяет строки исходников, а не реальный вызов MainForm.

Дополнительные воспроизведения находятся в [reviews/2026-10-22-claude](../reviews/2026-10-22-claude/). Это **контрпримеры для ревью**: на рассматриваемой main ожидается ненулевой exit code, поскольку проверки обнаруживают описанные дефекты. Они расположены отдельно от стандартного набора, чтобы не подменять его результат и не менять production-код в запросе на оценку.

```sh
python -m pip install -r tests/requirements-offline.txt
python reviews/2026-10-22-claude/reproduce_paused_order.py
dotnet run --project reviews/2026-10-22-claude/SnapshotCounterexamples.csproj --configuration Release
```

Lua: одна падающая проверка нового порядка. C#: две падающие файловые проверки; Cancel/RecoveryGate печатают отдельные наблюдения. На Linux в данной среде .NET CLI запускается с `DOTNET_CLI_TELEMETRY_OPTOUT=1 DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1`; это настройка CLI, не ослабление тестов. Опционально `TF3_REVIEW_BASELINE=1` у Lua-примера берёт scheduler из базы `52b47bd`: проверка порядка проходит, при этом старая вечная блокировка остаётся видна в наблюдениях.

## Следующие действия

Сначала исправить потерю зависимых команд и безопасный выход из failed recovery, затем перенести исправления жизненного цикла из PR #20 и убрать неоднозначность номера пакета. После компонентных проверок нужен повтор на двух игровых ПК: медленная передача/докачка, Cancel/Close, покупка и создание линии на паузе с задержанным ответом, failed recovery, уход/возвращение клиента и сохранение компаний.

Причина реального провала скорости .6 около 64 МиБ этими изменениями и проверками не установлена. TF3, пользовательские игровые сохранения и Porthole при этой оценке не запускались. Зелёный CI подтверждён; отсутствие игровых ошибок им не доказано.
